# app-008: The app's release build keeps the classes that JNI names

- Status: accepted
- Date: 2026-10-19
- Canonical source: tickets/2026-10-19-36-fix-android-release-start-with-shared-preferences.md
  (the user's choice of 2026-10-19: a keep rule instead of a pin of
  `shared_preferences_android` below 2.5.0; Findings)
- Refines: [release-004](release-004.md) — a release is checked on the
  Galaxy Tab S4
- Open work: drop the rules once `shared_preferences_android` and
  `package:jni` ship consumer rules for the Kotlin classes JNI names; a
  smoke test of a release build on a device (the app starts and reads its
  preferences) in the release checklist

## Decision

R8 shrinks and renames the Android release build of the Audanika app, so
every class that native code or JNI reaches by its name is kept in
`android/app/proguard-rules.pro`, which Flutter's Gradle plugin applies to
release builds. Since ticket 36 the file keeps the classes of
`io.flutter.plugins.sharedpreferences`, `kotlin.Result` with its inner
classes, `kotlin.Unit`, `kotlin.enums.EnumEntries`,
`kotlin.jvm.internal.DefaultConstructorMarker` and all of
`kotlin.coroutines`, so that a lookup of a later `package:jni` in the
coroutine classes finds its class too.

## Why

- `shared_preferences_android` 2.5.0 calls its Kotlin side through Pigeon
  JNI with `package:jni` 1.1.0, whose consumer rules keep only
  `com.github.dart_lang.jni.**`. R8 renamed `kotlin.coroutines.Continuation`
  and the Kotlin classes jni looks up by name; the lookups failed and app
  4.4.0 hung on its splash screen on Android, while debug builds and iOS
  ran.
- A keep rule fixes the app without holding back the plugin; a pin below
  2.5.0 would have stopped its updates.
