# seq-001: The sequencer runs on the render thread against the Transport

- Status: proposed
- Date: 2026-10-07
- Canonical source: topics/graph-engines-and-audiokit.md (R15),
  decisions/link-001.md
- Open work: tempo map and time signatures in v1 or later; clip
  launching semantics

## Decision

`aud_audio_sequencer` is a C++ sequencer stage that runs on the render
thread before the graph: tracks hold time-ordered events (notes, CCs,
OSC parameter messages) at beat positions in clips with loop length; per
block it reads the transport snapshot (time-001), derives clip positions
from the session beat (position = session beat minus launch beat,
modulo clip length), converts event beats to host times with the
snapshot and to sample offsets with the block's output time, handles a
block that spans the loop point, keeps the set of running notes for
note-offs on stop or seek, launches and stops clips on quantum
boundaries (Link's request-beat-at-time and start/stop sync), schedules
events early by the latency of the path to the output that the compiler
reports, and emits them into the target nodes' event inlets with sample
offsets. Sequences are published atomically
from Dart; seek, tempo and transport commands travel through the
command queue. The Dart model (`Sequence`, `Track`, `Clip`, `Event`) is
what the piano roll edits.

## Why

- AudioKitEX's SequencerEngine shows the render-thread design is
  simple, sample-accurate and glitch-free with live edits.
- Decoupling from Link through `Transport` keeps the sequencer usable
  in tests, on the web and inside plugin hosts.
