## Decision

On Windows `aud_audio_io` lists the active render and capture endpoints of
`IMMDeviceEnumerator` — endpoint id, friendly name, the channels and the
rate of the shared-mode mix format, the route from the form factor and the
bus, the defaults of the console role — and opens them with miniaudio's
WASAPI backend in shared mode, always by endpoint id and with automatic
stream routing off: a stream without a device id opens the current default
and reopens on the next one when the default changes, as on macOS. A stream
that asks for no rate runs at the mix format's rate, and miniaudio, not
Windows, converts any other rate (`noAutoConvertSRC`), so that
`IAudioClient3::InitializeSharedAudioStream` grants the low-latency period
— 256 frames by default, rounded to the engine's fundamental period. The
audio thread joins MMCSS "Pro Audio" in the low-latency mode. An
`IMMNotificationClient` hands its events to a COM thread of the backend:
a removed or disabled endpoint, a new default and a new mix format reopen
the streams they concern, and a miniaudio device that stops without being
asked counts as a loss. Host times are estimates as on macOS: the callback
time plus the block and the stream latency of the audio client. The hook
builds the backend for Windows only; the native tests build its file empty
and keep the null device.

## Why

- miniaudio is vendored already (io-001, io-004), and its WASAPI backend
  opens `IAudioClient3` shared streams itself — the latency io-001 wanted
  from a dedicated backend, without one.
- Following the default by reopening keeps the one recovery path of every
  platform; miniaudio's own rerouting would change format and period behind
  the stream's back.
- Shared mode is what Microsoft recommends first and what other apps keep
  playing beside; exclusive mode waits for S3d (the plan review).
