# web-001: One WebAssembly module per AudioContext, Dart on the main thread

- Status: proposed
- Date: 2026-10-07
- Canonical source: topics/dart-interop-and-web.md,
  topics/audio-io-platforms.md (Web)
- Open work: decide whether the web build of an app links the DSP
  packages through a generated Emscripten build (`aud_audio_web`) or
  through prebuilt per-package Wasm archives

## Decision

On the web the engine and every DSP node are compiled by Emscripten into one
WebAssembly module per `AudioContext` (static linking at app build time,
driven by `aud_audio_web`), loaded into an `AudioWorkletGlobalScope` with
`-sAUDIO_WORKLET -sWASM_WORKERS`. Dart (dart2js or dart2wasm) runs on the main
thread, uses the same `aud_audio` API as on native, and reaches the module
through `dart:js_interop` and `package:web`: commands over a `MessagePort`,
audio and event data through `SharedArrayBuffer` ring buffers when the page is
cross-origin isolated, with a `MessagePort`-only fallback otherwise; a Wasm
Worker takes the role of the native control thread (web-002); web-003 states
the capabilities of each environment, abi-001 the contribution manifest of the
packages. `aud_audio_io` on the web is the worklet host plus `getUserMedia`
input and `destination.channelCount` output; `setSinkId` is a capability flag.

## Why

- `dart:ffi`, isolates and build hooks do not exist on the web.
- Emscripten issue 25788: two modules on one context corrupt memory.
- flutter_soloud proved the worklet-when-isolated, fallback-otherwise
  pattern in a shipping Flutter package.
