# web-003: The web capability contract

- Status: proposed
- Date: 2026-10-08
- Canonical source: topics/review-2026-10-08-plan-scope.md (point 5);
  decisions/web-001.md, web-002.md
- Open work: measure the memory ceilings and the fallback latency in
  S0-web; decide whether the non-isolated path ships in M2 or later

## Decision

"All platforms" is stated as capabilities per environment, and the
documentation and the API report them:

| Capability | Native | Web, cross-origin isolated | Web, not isolated |
| --- | --- | --- | --- |
| Control runtime | control thread | Wasm Worker sharing the heap | worker without shared memory; plans and assets transferred by message |
| Event timing | sample-accurate, lookahead queue | same, over shared ring buffers | sample-accurate only for events scheduled at least one block plus the message latency ahead |
| Meters and analysis | ring buffers | shared ring buffers | sampled at a lower rate over messages |
| Sample loading | file system, streaming | fetched on the main thread into shared memory | fetched on the main thread, copied into the worklet |
| Recording | duplex streams | `getUserMedia` into shared memory | `getUserMedia` over messages, higher latency |
| Device selection | full | `setSinkId` in Chromium only | same |
| Memory | device-dependent budgets | the browser's Wasm memory ceiling, budgets per browser | same, plus the copies of transferred assets |
| Module delivery | build hooks | the main thread compiles the module and posts it to the worklet, which has no `fetch` | same |

The non-isolated path is a distinct implementation, not a degraded flag;
S0-web proves both paths with a representative sampler workload, asset
loading and sustained playback, not with a sine.

## Why

- Each AudioContext has one audio-processing thread, worklets cannot
  spawn general-purpose threads and lack `fetch`; without shared memory
  the timing and loading model changes.
