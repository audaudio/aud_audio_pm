# 5: Spike the mobile foundation on iOS and Android

## Goal

Prove the mobile foundation of milestone M1 before the core tickets start
— step S0-mobile of the plan of ticket 17 (release-002), the gate of S1 to
S4: (a) a C++ sine reaches the device on iOS and Android through a
`package_ffi` hook build, controlled from Dart, with measured callback
period and command latency; (d) the sfizz fork builds for iOS and Android
(clang-19 fix) and a legacy preset plays sustained for ten minutes; (e) two
separately built DSP packages register nodes through the C ABI into one
engine; (f) the core packages install and test with the Dart SDK alone, no
Flutter. The spike's code is written into the packages where it will live,
as the seed of S1 to S4, S9 and S10a, and its findings feed the contracts
of those tickets. Serves [flutter-audio-kit](../goals/flutter-audio-kit.md).

## Affected repos

- `aud_audio_pm`: this plan with the findings; decision build-001.
- `aud_audio_core`: `src/aud_abi.h`, the first cut of the C ABI
  (abi-001: sized structs, major and minor version, capabilities, thread
  affinity tags on every vtable entry, host callbacks with allocator
  ownership, the node vtable, the render callback of plugin-002);
  `aud_clock.h`, the monotonic host clock of time-001; `aud_spsc_queue.hpp`,
  the lock-free single-producer queue of interop-002. Dart: `AudAbi` with
  the version, the struct-size check against C and the result code names;
  the ABI structs generated by ffigen. Header only — packages include the
  core, they never link it.
- `aud_audio_graph`: the spike engine `AudEngine`: node types registered
  through the host api with the ABI version gate, persistent node
  instances in fixed slots, a serial chain as the render program that the
  realtime thread adopts at the block start and acknowledges by revision
  (graph-003 in small), the command queue with capacity, overflow error
  and per-block budget (interop-002), command latency and render time
  counters, ping-pong buses for nodes that do not render in place; the
  reference nodes `aud.ref.sine` and `aud.ref.gain`.
- `aud_audio_io`: the spike stream `AudIoStream` on miniaudio 0.11.25
  (macOS, iOS; vendored single header) and Oboe 1.11.0 (Android; vendored
  sources compiled by the hook, io-002) with the callback timing counters
  and the null backend for tests; `NOTICES.md` for both.
- `aud_dsp_effects`: `aud.effects.tremolo` and the registration entry
  point `aud_dsp_effects_register` — the first separately built DSP
  package.
- `aud_dsp_sampler`: `aud.sampler.sfz` on sfizz with the vendored subset
  of the audanika fork — the 112 translation units the linker pulls and
  their header closure, listed in `SOURCES.txt` and `INCLUDES.txt` —,
  loading by file or by SFZ text with a virtual path, note and control
  events, the volume parameter; `NOTICES.md` with every component's
  license.
- `aud_audio`: the example app of the umbrella with the spike graph: sine
  → tremolo, the legacy sine sample set through the sampler, the sustained
  test and the measurement panel. The app depends on graph, io and the two
  DSP packages directly until S4 gives the umbrella its `Engine`.
- `aud_audio_web`: unchanged; in the ticket because it sits between the
  umbrella and graph and io.

## Findings

Gate (f), the core packages with the Dart SDK alone: `dart pub get`,
`dart analyze` and `dart test` of `aud_audio_core` and `aud_audio_graph`
run without Flutter; the build hooks compile the C and C++ on the host.
Nothing in the dependency closure of the core packages needs the Flutter
SDK.

Gate (a), the sine on the device: the reference sine of the engine reaches
the output on the iOS simulator through miniaudio/Core Audio and on the
Android emulator through Oboe/AAudio, both through `package_ffi` hook
builds, controlled from Dart through the command queue; the engine's
output peak meter reads 0.30 for the sine at gain 0.3 through the tremolo.
Measured with debug builds at 48 kHz, stereo (the hooks compile with -O3
in every mode):

| | iOS simulator (iPhone 17 Pro, iOS 26.2) | Android emulator (API 36, arm64) |
| --- | --- | --- |
| Backend | miniaudio/Core Audio | oboe/aaudio, legacy path, no low latency |
| Frames per callback | 256 (5.33 ms) | 960 burst (20 ms), callbacks of 8 to 960 frames |
| Callback period mean / max | 5.33 ms / 10.9 ms | 10.0 ms / 65 ms |
| Time in the callback mean / max | 0.011 ms / 0.026 ms (sine, 0.5 % of the block), 0.047 ms / 1.4 ms (sampler, 26 %) | 0.02 ms / 0.5 ms (sine, 2.5 %), 0.07 ms / 5.9 ms (sampler, 29 %) |
| Command latency (enqueue to apply), 100 parameter changes after a reset | 4.35 ms mean, 4.34 to 4.37 ms (all in one block) | 0.94 ms mean, 0.94 to 0.95 ms (all in one block) |
| Commands rejected | 0 | 0 |
| Xruns reported by the backend | not available | 0 |
| Output latency reported by the backend | not available | 161 to 171 ms (emulator) |
| Sustained test (random note every 400 ms through the sampler) | 10 min 41 s, 136 593 callbacks, 3306 commands, 0 disconnects | 10 min 20 s, 68 253 callbacks, 3208 commands, 0 xruns, 0 disconnects |

Reading the numbers: the simulator's HAL runs 512-frame periods while the
stream asks for 256, so callbacks arrive in pairs (period minimum 0.003 ms,
maximum 10.8 ms) — the late-callback counter flags every second one; a real
device delivers one callback per period. The Android emulator has no
low-latency path (AAudio legacy, 20 ms bursts, 171 ms output latency); the
numbers for the budgets of the verification section need the reference
devices (open question 6 of ticket 17). The command latency is bounded by
the block period as designed: a command waits for the next block start. A
command enqueued before the stream starts waits until it does, which the
first pass showed as an outlier of 43 s and 85 s; the engine got
`resetStats` so that measurements start clean. The time in the callback
stays far below the block on both platforms; the sampler's voice starts
are the costliest blocks (1.4 ms and 5.9 ms), which the budgets of the
verification section will measure on the reference devices.

Gate (e), two separately built DSP packages: `aud_dsp_effects` (tremolo)
and `aud_dsp_sampler` (sfizz) are compiled by their own hooks into their
own libraries and register their node types at run time through the
`AudHostApi` pointer of the engine; on Android each library is a
separate `.so` in the APK, on iOS a separate framework. The ABI gate works
as specified: the engine refuses a descriptor of another major and a newer
minor, a duplicate type id and a descriptor without a vtable (tested from
Dart through the host api pointer). The packages never link the engine or
the core; the core is included as headers resolved through the package
config.

Gate (d), sfizz: the audanika fork builds for macOS, iOS (simulator,
arm64 and x86_64) and Android (arm64 and x86_64) with no source change —
the fork's master (2026-02, "Update atomic_queue to v1.6.9") already
compiles with clang 19 (NDK r28c) and Apple clang 21; the clang-19 fix of
sampler-001 is done. The subset the sampler needs is 117 translation
units (sfizz, 16 of Abseil, st_audiofile with dr_libs, WavPack and
libaiff, pugixml, KISS FFT, cephes, the tuning library, cpuid, the
filesystem implementation) with 420 headers, 7.9 MB vendored, compiled by
the hook in one library. The legacy sine sample set of the Audanika app
(`AUD007869_sineWave.sampleset`, the sound of the Combi preset) plays
through the sampler node on both platforms, converted to SFZ text at
start-up; the sustained test plays a random note every 400 ms.

Findings for the later tickets:

- Hooks have no per-file compiler flags: sfizz's AVX objects need
  `-mavx` on x86_64, so the sampler library is built for AVX on x86_64
  as a whole (build-001).
- Mixed C and C++ sources leave no room for a `-std` flag; the own code
  of such a package stays within the default standard of the toolchain
  (gnu++14 on Apple clang 21 for the node code: no `std::clamp`).
- On Android the hook must link `libm` explicitly; `sin` is otherwise an
  unresolved symbol at load time (`dlopen` fails for the whole library).
- miniaudio needs an Objective-C++ translation unit on iOS
  (AVAudioSession), so the IO package compiles `aud_io_miniaudio.mm`.
- `CLOCK_MONOTONIC` has microsecond resolution on Apple platforms;
  `aud_clock_now_ns` uses `CLOCK_UPTIME_RAW` there, the clock of
  `mach_absolute_time` that Link uses (time-001).
- sfizz loads only while no realtime call is in flight (its CT/OFF tags);
  the spike loads before the node enters the chain. S2 needs the general
  rule (open question 2).
- The variable callback sizes of AAudio's legacy path (8 to 960 frames)
  are real: graph-002's variable blocks are the right model.
- The emulator and the simulator give no latency or xrun numbers worth
  recording; the reference devices do (open question 6 of ticket 17).

## Open questions

1. The spike keeps every third-party source in the package (`src/third_party`)
   with a `SOURCES.txt` manifest for the hook. Is a build-time fetch (as
   link-002 prescribes for Link) wanted for sfizz, Oboe and miniaudio too,
   or stays vendoring the rule for permissive sources (build-001)?
2. sfizz forbids loading while a realtime call is in flight (its CT/OFF
   tags). The spike loads before the node enters the chain. S2 needs the
   general rule: a control-thread operation that takes a node out of the
   program, waits for the acknowledgement and puts it back — or a loading
   scheme inside the node (sfizz's own callback guard renders silence
   while loading, which the contract does not promise).
3. The example app depends on graph, io and the DSP packages directly;
   S4 moves this behind the umbrella's `Engine`.
4. Which real devices run the spike app first? The paired iPad needs the
   one-time signing setup in Xcode; an Android phone with a low-latency
   AAudio path gives the first numbers worth comparing with the budgets.
